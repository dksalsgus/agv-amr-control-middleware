# 측정 결과

`node scripts/measure.mjs`를 다섯 번 돌린 결과를 범위(최소~최대)로 적습니다. 한 번 실행하면 아래 다섯 절이 표로 나오고, 실행 끝에 에뮬레이터 컨테이너를 다시 켜므로 다음 실행은 폴링 위상이 달라집니다.

- **언제, 어디서**: 2026-11-19 18시 KST, 리눅스 컨테이너(CPU 4개) 한 대의 docker compose. 로봇 90대와 PLC 16점.
- **시계**: 스크립트, 미들웨어, 에뮬레이터가 같은 리눅스 호스트 시계를 씁니다. Mac의 Docker Desktop에서 돌리면 스크립트는 Mac 시계, 에뮬레이터는 VM 시계를 써서 **종단 지연**에 두 시계의 차이가 섞일 수 있습니다. 수집 지연은 둘 다 VM 안이라 영향이 없습니다.
- **다시 재기**: docker compose를 띄운 뒤 저장소 루트에서 `node scripts/measure.mjs` (Node 22, 의존성 없음, 약 2분 30초).

## 읽는 법

- **수집 지연**은 미들웨어가 받은 시각에서 장비의 발생 시각을 뺀 값이고, **종단 지연**은 화면(측정 스크립트의 WebSocket)이 delta를 받은 시각에서 발생 시각을 뺀 값입니다.
- **폴링 연결(B는 REST, C와 PLC는 Modbus)의 지연은 위상에 따라 정해집니다.** 에뮬레이터 갱신과 폴링이 둘 다 1초(PLC 폴링은 0.5초) 주기라, 데이터가 생긴 뒤 다음 폴링까지 기다리는 시간이 한 번 띄운 동안에는 거의 고정되고, 다시 띄울 때마다 0~1초 사이 어딘가로 바뀝니다. 그래서 한 실행의 p95는 분포가 아니라 그 실행의 위상 하나입니다. 이론 범위는 "0~폴링 주기 + 처리 시간"이고, 아래에는 다섯 번 잰 범위를 적습니다. B와 C 중 어느 쪽이 빠른지는 실행마다 바뀝니다.
- 수치 대부분은 미들웨어가 스스로 센 `/metrics` 값입니다. MQTT를 직접 구독해 센 독립 계수와 받은 메시지 수가 같다는 것은 따로 확인했지만, 스크립트만으로 교차 검증하지는 않습니다.

## 1. 정상 30초: 지연과 건너뛴 seq

PLC 값은 장애 주입으로만 바뀌므로, 이 구간 동안 스크립트가 PLC 0번 점을 2초마다 켜고 꺼서 PLC 지연 표본을 만듭니다.

| 연결             | 폴링 주기  | 수집 지연 p95 (5회 범위) | 종단 지연 p95 (5회 범위) | 건너뛴 seq 비율   |
| ---------------- | ---------- | ------------------------ | ------------------------ | ----------------- |
| A (MQTT)         | 없음(push) | 6~10 ms                  | 57~104 ms                | 5회 모두 0%       |
| B (REST)         | 1초        | 74~865 ms                | 146~964 ms               | 4회 0%, 1회 3.23% |
| C (Modbus TCP)   | 1초        | 171~760 ms               | 239~825 ms               | 5회 모두 0%       |
| PLC (Modbus TCP) | 0.5초      | 104~492 ms               | 154~524 ms               | 4회 0%, 1회 1.64% |

| 프로세스 (5회 범위)        | 값         |
| -------------------------- | ---------- |
| CPU 평균 (코어 1개 = 100%) | 8.3~11.9%  |
| CPU 최대                   | 12.9~18.4% |
| RSS                        | 169~175 MB |
| heap 사용                  | 48~57 MB   |

**장애가 없는데 seq를 건너뛴 경우**: 폴링 위상이 갱신 경계(0초나 1초 근처)에 걸린 실행에서만 나옵니다. 타이머가 조금씩 흔들려 두 번의 폴링 사이에 갱신이 두 번 일어나면 가운데 seq 하나를 읽지 못합니다. 장비가 보낸 데이터가 사라진 것이 아니라 폴링이 상태 하나를 못 본 것이고, 다음 폴링에서 최신 상태를 받습니다. 폴링 방식의 성질이라 결함으로 고치지 않았습니다.

## 2. 제조사 A에 중복 30%·뒤바뀜 30%·유실 10% 주입 15초

| 항목 (5회 범위)                             | 값                   |
| ------------------------------------------- | -------------------- |
| 받은 메시지                                 | 664~697              |
| 중복으로 버림                               | 122~145              |
| 늦게 와서 버림 (늦게 온 메시지의 중복 포함) | 99~123               |
| 화면에 반영 못 한 seq                       | 134~156 (23.3~26.7%) |
| 그중 끝내 오지 않은 seq (하한)              | 19~42                |
| 화면에서 seq가 뒤로 간 횟수                 | 5회 모두 0           |

- **반영 못 한 seq**는 두 가지가 섞인 값입니다. 하나는 끝내 오지 않은 메시지(주입한 유실)이고, 다른 하나는 다음 seq가 먼저 와서 늦게 도착한 메시지를 버린 것(주입한 뒤바뀜)입니다. 그래서 주입한 유실 10%보다 크게 나옵니다.
- 미들웨어는 늦게 온 메시지의 중복도 늦음으로 세므로, 끝내 오지 않은 seq는 "반영 못 한 seq − 늦게 와서 버림"을 하한으로만 적습니다.
- 늦게 온 메시지를 버리는 것은 화면 seq가 뒤로 가지 않게 하려는 설계입니다(설계 문서 8장 장애 시나리오).

## 3. 현장 연결 끊김 복구 (장애 주입)

에뮬레이터의 끊김 장애를 켜서 DOWN이 되기까지, 끊김을 풀고 UP이 되기까지, 그 뒤에 발생한 새 데이터가 화면에 처음 닿기까지의 시간입니다.

| 그룹             | DOWN 감지 (5회 범위) | UP까지      | 첫 새 데이터까지 |
| ---------------- | -------------------- | ----------- | ---------------- |
| A (MQTT)         | 4.6~5.0 s            | 0.20~1.11 s | 0.18~1.07 s      |
| B (REST)         | 2.1~3.0 s            | 1.01~1.11 s | 0.98~1.08 s      |
| C (Modbus TCP)   | 2.9~3.8 s            | 1.81~1.91 s | 1.77~1.86 s      |
| PLC (Modbus TCP) | 2.5~2.9 s            | 1.76~1.81 s | 1.86~2.06 s      |

A는 메시지가 끊긴 시간으로 DOWN을 판정하고, B·C·PLC는 폴링 3번 연속 실패로 판정합니다. PLC는 값이 자주 바뀌지 않으므로 "첫 새 데이터"를 stale이 풀린 점이 화면에 닿은 때로 셉니다.

## 4. 화면 재접속 복구

| 방식                               | 소켓을 연 뒤 첫 응답까지 (5회 범위) |
| ---------------------------------- | ----------------------------------- |
| 이어받기 (epoch + lastRev → delta) | 4~6 ms                              |
| 처음 접속 (snapshot 전체)          | 4~9 ms                              |

스크립트와 미들웨어가 같은 컴퓨터에 있어 네트워크 지연이 거의 없는 값입니다. 소켓을 다시 연 뒤부터 잰 값이라, 화면이 끊김을 알아채는 시간(ping 2회 무응답)은 들어 있지 않습니다. 실제 네트워크에서는 왕복 시간만큼 더 걸립니다.

## 5. 에뮬레이터 컨테이너 재시작 복구

장애 주입이 아니라 `docker compose stop emulator`로 프로세스를 멈춘 뒤 DOWN이 되기까지, `docker compose start emulator` 뒤 UP과 첫 새 데이터까지의 시간입니다. 에뮬레이터 부팅 시간이 들어 있습니다.

| 그룹             | DOWN 감지 (5회 범위) | UP까지      | 첫 새 데이터까지 |
| ---------------- | -------------------- | ----------- | ---------------- |
| A (MQTT)         | 2.4~4.0 s            | 1.89~2.02 s | 1.87~1.98 s      |
| B (REST)         | 2.4~2.7 s            | 3.48~4.91 s | 3.48~4.97 s      |
| C (Modbus TCP)   | 2.2~3.1 s            | 1.09~4.30 s | 1.07~4.30 s      |
| PLC (Modbus TCP) | 1.3~1.7 s            | 2.73~3.90 s | 2.97~4.37 s      |

재시작 뒤 복구가 끊김 장애보다 느린 것은 DOWN 동안 재접속 간격이 1초에서 두 배씩 늘어나 있어서, 에뮬레이터가 다 뜬 뒤 다음 재시도까지 기다리기 때문으로 보입니다. 가장 느린 경우도 목표(10초) 안입니다.
